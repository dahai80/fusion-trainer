# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Fusion-Trainer is a lightweight supervised + reinforcement learning trainer on Apple MLX for Mac M5 unified memory. It is a **pure computation/orchestration layer** — it never imports `mlx-lm`/`mlx-vlm` directly. All training, sampling, and reward scoring is delegated to **fusion-mlx over HTTP**. It provides SFT fine-tuning, RLSL/DPO/ORPO/GRPO alignment, reward-model training, dataset loading, and experiment tracking — all local-first, no cloud dependency.

**Current state (v1.0.0rc16):** All training loops are **real**, not scaffolded. SFT (LoRA/DoRA/full/QLoRA) for text LM models **and** VLM fine-tune for vision-language models, DPO, ORPO, reward-model training, and GRPO all run real gradient loops inside fusion-mlx, driven over HTTP job endpoints. **TTS voice-pack fine-tune ([#74](https://github.com/dahai80/fusion-trainer/issues/74)) is wired** — `ft voice-train` trains a Kokoro voice package through fusion-mlx `POST /admin/api/fine-tune/voice/jobs` ([fusion-mlx#1336](https://github.com/dahai80/fusion-mlx/issues/1336), gradient-free SPSA), with `--publish` registering it in fusion-model-hub as `model_type=audio`. The RLSL closed loop (RM train → reward/score → policy-gradient GRPO) is real end-to-end. Trained LoRA adapters can be published to fusion-model-hub on completion (`--publish` flag or `publish <run_id>` subcommand, issue #49, PR #51). v0.1.11 closed all 13 defects from the adversarial audit (`audit/fusion-trainer-audit-0901.md`): reward-server token auth + path validation, sandbox code-mode default-off + env gate, per-prompt top-k, mxfp8 default-off + fail-stop, HTTP connection reuse + retry/backoff, RunManager singleton, atomic meta writes, publish 409 idempotency, and a contract integration test. **All former upstream blockers are now closed** — MXFP8 ([fusion-mlx#402](https://github.com/dahai80/fusion-mlx/issues/402)) routes to 8-bit QLoRA (8-bit frozen base + LoRA, not fp8 compute; MLX 0.32 has no fp8 dtype), GRPO true backend ([fusion-mlx#751](https://github.com/dahai80/fusion-mlx/issues/751)) is fixed (worker rebinds `generation_stream`), OS-level sandbox ([fusion-mlx#743](https://github.com/dahai80/fusion-mlx/issues/743)) shipped server-side `code_sandbox.py`, and GUI publish ([fusion-studio#390](https://github.com/dahai80/fusion-studio/issues/390) + fusion-agent-studio#277) works natively. **VLM fine-tune ([#55](https://github.com/dahai80/fusion-trainer/issues/55)) is now wired** — `model_type=="vlm"` routes to fusion-mlx's VLM endpoint ([#797](https://github.com/dahai80/fusion-mlx/issues/797)→[#800](https://github.com/dahai80/fusion-mlx/pull/800), v0.8.80), driving `mlx_vlm.trainer` SFT/LoRA over HTTP. `use_mxfp8` defaults to `False`; an explicit `True` passes through to fusion-mlx (mxfp8+full still fails visibly — full unfreezes the base). **Checkpoint resume ([#65](https://github.com/dahai80/fusion-trainer/issues/65)) is wired** — `ft sft --resume` / `ft bnup-train --resume` continues an interrupted run from the newest numbered checkpoint via fusion-mlx [#1182](https://github.com/dahai80/fusion-mlx/issues/1182) `init_adapter_path` (v0.10.12+), with engine-restart detection (404 poll / restart-recovery cancelled → `interrupted` + checkpoint hint, never zombie-polling). **Benchmark-based checkpoint selection ([#75](https://github.com/dahai80/fusion-trainer/issues/75)) is wired** — `ft sft --eval-select` benchmarks every numbered checkpoint through fusion-bench's task API and picks the winner deterministically (bench score → val_loss → last checkpoint), persisting `checkpoint_selection.json` atomically; bench outage falls back to val_loss with a persisted `fallback_reason` (fail-visible, never a silent mis-selection). `grpo_backend` gains the honest `policy_gradient` alias (normalized to `grpo`) and docs state plainly that default `rft` is a reward-filtered SFT approximation, not true GRPO. `DatasetLoader.load_messages` now caps the whole conversation at `max_seq_length * 4` chars (trailing turns, never mid-answer) instead of the old ~4x over-truncating per-message char cap. Nightly real-training CI (`.github/workflows/nightly.yml`) ungates `TestRealFusionMLXIntegration` + contract tests on a macOS arm64 runner with a live fusion-mlx + `Qwen3-0.6B-4bit`; it installs base (slim) `fusion-mlx>=0.10.17` — the slim install works since [fusion-mlx#1403](https://github.com/dahai80/fusion-mlx/issues/1403)/#1406 and running slim keeps that path covered. **Sequence packing is wired (v1.0.0rc16)** — `ft sft --pack-sequences` / YAML `pack_sequences: true` passes `pack_sequences` to fusion-mlx (>= 0.10.17, [fusion-mlx#1400](https://github.com/dahai80/fusion-mlx/issues/1400) closed): rows up to `max_seq_length` tokens, block-diagonal attention mask, per-token loss mask honouring `mask_prompt`; key only sent when on (older fusion-mlx 400s on it); off by default (changes batch composition). Bench adapter scoring is real: [fusion-bench#29](https://github.com/dahai80/fusion-bench/issues/29) closed in v0.4.11 forwards `params.adapter_path` to fusion-mlx chat as `adapters` — the params form is sent deliberately for old-bench compat.

## CLI Entry Points

```bash
fusion-trainer sft --config configs/sft_7b.yaml --model qwen2.5-7b-4bit --dataset /path/to/data.jsonl
fusion-trainer rlsl --config configs/rlsl_14b.yaml --model qwen2.5-7b-4bit --dataset /path/to/pref.jsonl --method dpo
fusion-trainer info
ft sft ...    # short alias
```

There is **no `dataset` subcommand** — dataset import/list/info is handled by the companion project `fusion-model-hub`. The CLI has `sft`, `rlsl`, `info`, `publish`, `bnup-prep`, `merge`, `bnup-train`, `voice-train` (plus `--version`).

- `fusion-trainer publish <run_id> [--hub-url URL --hub-api-key KEY]` — retroactively publish a completed run's LoRA adapter to fusion-model-hub. Reads adapter_name + base model from the run registry. This standalone op exits non-zero on failure (E6: so CI/`&&` chains detect it); the in-training `--publish` flag stays non-blocking by design.
- `sft`/`rlsl` also accept `--publish` to publish on completion, and `--model-hub-path` to override the read-only hub dataset path.
- `ft bnup-prep --stage sft|dpo --input <file> --output <file> [--system-prompt ...] [--neg-ratio N]` — prepare BNUP training data. SFT stage validates DSL via fusion-core + builds `<thinking>`+`<dsl>` ShareGPT JSONL; DPO stage generates neg_ratio negative variants per sample (issue #56/#57).
- `ft merge --base <model> --adapter <path> [--output <dir>] [--quantize 4bit|8bit] [--dequantize] [--publish]` — merge a trained LoRA/DoRA adapter into the base model via fusion-mlx POST /v1/merge-adapter, optional post-merge quantization (issue #58).
- `ft bnup-train --stage sft|dpo|pipeline --model <model> --sft-data <data> [--dpo-data <data>] [--sft-config ...] [--dpo-config ...] [--merge-output <dir>] [--init-adapter-path <p>]` — run BNUP two-stage training (SFT → DPO → merge). The `pipeline` stage auto-chains DPO on the SFT adapter (fusion-mlx #1149); `--init-adapter-path` chains a standalone `dpo` stage manually. Uses `bnup_sft_32b`/`bnup_dpo_32b` presets by default (issue #59).
- `ft voice-train --model <kokoro-model> --dataset <dir> [--voice-id ... --steps N --base-voice ... --lang-code ... --max-samples N --seed N --tenant-id ... --publish]` — train a TTS voice pack via fusion-mlx `/admin/api/fine-tune/voice/jobs` (issue #74). Validates the dataset locally first, polls the job to terminal, prints `voice_ref` + spectral-distance metrics; non-completed exits 1. `--publish` registers the package in fusion-model-hub as `model_type=audio` (non-blocking).

## Architecture

```
CLI (cli.py)
  ├── SFT path: SFTTrainer → DatasetLoader, LoRAConfig, ExperimentLogger
  │            ├── model_type="lm"  → stage_dataset → create_job → wait_for_job
  │            │                       (text SFT: real mlx-lm gradient loop in fusion-mlx)
  │            └── model_type="vlm" → _build_vlm_config → create_vlm_job → wait_for_vlm_job
  │                                    (VLM SFT: real mlx_vlm gradient loop in fusion-mlx, #55/#797/#800)
  │                                    (NO stage_dataset — mlx_vlm consumes raw HF-id/local-dir dataset ref)
  └── RLSL path: RLSLEngine dispatches by rlsl.method:
                    ├── dpo  → DPOTrainer      → create_dpo_job  (/admin/api/fine-tune/dpo/jobs)
                    ├── orpo → ORPOTrainer     → create_orpo_job (/admin/api/fine-tune/orpo/jobs)
                    ├── grpo → GRPOTrainer
                    │            ├── grpo_backend="rft"  → on-policy sample → sandbox score → top-k → SFT job
                    │            └── grpo_backend="grpo" → RewardServer (local HTTP) + create_grpo_job
                    │                                        (/api/fine-tune/grpo/jobs, fusion-mlx #363)
                    └── rlsl → Phase 1 RewardTrainer (train RM #424)
                               → Phase 2 RMRewardServer + real GRPO (#363), scored via reward/score (#431)
```

The single HTTP boundary is **`MLXFineTuneClient`** (`mlx_client.py`). Every trainer builds a config dict, submits a job, then polls with `wait_for_job` / `wait_for_vlm_job` / `wait_for_grpo_job` / `wait_for_dpo_job` / `wait_for_reward_job`. Job `events` (train_loss, val_loss, grpo_step) are streamed into `ExperimentLogger`. Real adapter weights land in `~/.fusion-mlx/adapters/<model>/<name>/`; the trainer writes only a local pointer `adapter_config.json`.

### Publish-to-hub flow (issue #49, PR #51)

On run completion (when `TrainerConfig.publish_adapter=True`, set by `sft`/`rlsl --publish`), the CLI and `RunManager._run_thread` call `hub_client.publish_adapter_if_enabled`. It builds a `ModelHubClient` (base URL from `hub_url` / `$FUSION_MODEL_HUB_URL`, key from `hub_api_key` / `$FUSION_MODEL_HUB_API_KEY`, default port 11432), locates the local adapter pointer + real weights, and POSTs them to the hub as `model_type=lora` with `base_model_id`. Failures warn loudly but do not fail the run (fail-visible, non-blocking). `RunManager.publish_run(run_id)` retroactively publishes any past completed run. The GUI path now forwards publish fields natively: fusion-agent-studio#277 fixed `TrainingService._build_trainer_config` to pass `publish_adapter`/`hub_url`/`hub_api_key`, and fusion-studio#390 exposed them in the Trainer panel — so GUI-triggered publish fires without the env-var bypass. (The legacy `FUSION_TRAINER_PUBLISH=1` / `FUSION_MODEL_HUB_URL` / `FUSION_MODEL_HUB_API_KEY` env fallback remains as an override.)

### Real GRPO reward-server callback

For `grpo_backend="grpo"` and RLSL Phase 2, fusion-mlx's server-side GRPO loop scores completions by **calling back a local HTTP server** the trainer hosts:
- `RewardServer` (sandbox reward: math/code) — `POST {prompt, completions} → {rewards}`
- `RMRewardServer` (trained RM adapter, via reward/score endpoint #431)

The server maps the prompt string back to its dataset sample (carrying reference answer/tests) and delegates to `sandbox.reward_completion`. Started/stopped around each job with a `try/finally`.

### Package Structure

- `mlx_client.py` — **`MLXFineTuneClient`**, the only fusion-mlx HTTP wrapper. All job endpoints (SFT/GRPO/DPO/ORPO/reward/score/VLM/adapters) + `stage_dataset` (writes chat-messages JSONL fusion-mlx consumes) + `merge_adapter` (POST /v1/merge-adapter, issue #58).
- `hub_client.py` — **`ModelHubClient`** + `publish_adapter_if_enabled`, publishes trained LoRA adapters to fusion-model-hub as `model_type=lora`, merged models as `model_type=mlx`, and trained TTS voice packages as `model_type=audio` (`publish_voice_package`, #74). Sends both `Authorization: Bearer` and `X-API-Key` (the hub's local middleware reads the latter). `HubPublishError` on failure.
- `voice.py` — **`VoiceTrainer`** + `VoiceTrainConfig` (#74): voice-pack fine-tune orchestration over HTTP (SPSA backend upstream). `model` must be a Kokoro-family id; returns the upstream terminal status + `voice_ref`/`voice_path`/metrics, never a faked completion.
- `merge.py` — **model merge + export** (issue #58): `merge_adapter` (fusion-mlx /v1/merge-adapter), `export_merged_model` (optional 4/8-bit quantize), `validate_merged_model` (format check on generation output), `merge_and_export` (full pipeline).
- `eval_loop.py` — **benchmark-based checkpoint selection (#75)**: `BenchClient` (fusion-bench task API over pure HTTP, `X-Tenant-Id` + Bearer, S6 URL guard), `list_checkpoints` (every `NNNNNN_adapters.safetensors`, generalizing #65's `find_latest_checkpoint`), `select_best_checkpoint` (deterministic: bench score → val_loss → last checkpoint), `run_checkpoint_eval` (stages each checkpoint to a servable `adapters.safetensors` dir, submits one bench task per candidate, persists `checkpoint_selection.json` atomically. Bench outage → `unavailable` rows + `fallback_reason` + val_loss selection, never raises, never silent. `SFTTrainer._run_checkpoint_eval` hooks it after a completed job when `sft.eval_select` (val_loss pairs tracked in `_ingest_progress`).
- `config.py` — `TrainerConfig` aggregates `DatasetConfig`, `SFTConfig`, `RLSLConfig`. `__post_init__` auto-fills `sft.output_dir`/`rlsl.output_dir` from `cache_path`. Also holds `hub_url`/`hub_api_key`/`publish_adapter` (publish-to-hub, off by default), `model_hub_path` (read-only hub dataset path), `cache_path`, `mlx_port`. **#80:** env defaults single-sourced via `fusion_core.config` v0.7.0 (pin bumped from v0.5.0) — `_default_mlx_port` = `service_port("MLX", 11434)`, hub url/key = `get_env` (same env names, no behavior change); `MLXFineTuneClient` engine token = `resolve_api_key(env_var="FUSION_MLX_ADMIN_TOKEN")` (env then `~/.fusion-mlx/settings.json` `auth.api_key`); bridge shell registration key = `fusion_core.config.admin_key` (env renamed `FUSION_GATEWAY_ADMIN_KEY` → `FUSION_ADMIN_KEY`; prod-missing degrades to disabled registration with a loud warning, never fatal).
- `sft/` — `SFTTrainer` (real HTTP loop), `LoRAConfig`, `presets.py` (`SFT_PRESETS`, 11 named configs including `bnup_sft_32b` with `memory_estimate_gb`).
- `rlsl/` — `RLSLEngine` (dispatch, in `pipeline.py`), `DPOTrainer` (`dpo.py`), `ORPOTrainer` (`orpo.py`), `RewardTrainer` (`reward.py`), `GRPOTrainer` (`grpo.py`), `sandbox.py` (deterministic math/code reward — Rule 5: no model routing), `reward_server.py` + `rm_reward_server.py` (local HTTP reward endpoints), `presets.py` (`RLSL_PRESETS`, includes `bnup_dpo_32b`).
- `dataset/` — `DatasetLoader` (`load` / `load_preference` / `load_messages` / `load_grpo`), `formats.py` (schema detection: messages/ShareGPT/DPO-pair/GRPO-prompt), `transforms.py`, `versioning.py`, `bnup_prep.py` (SFT data prep + DSL validation via fusion-core, #56), `bnup_dpo_prep.py` (DPO pair generation, #56), `bnup_negatives.py` (5 negative sample generators, #57), `voice_prep.py` (voice dataset layout validation for #74).
- `experiment/` — `ExperimentLogger` (memory-bounded `deque(maxlen=1000)` + JSONL streaming + TensorBoard on by default), `ExperimentTracker`, `TrainingVisualizer`.
- `run_manager.py` — **`RunManager`**, async run orchestration surface for the GUI path (start/progress/status/list/stop + presets/datasets/adapters listing + `publish_run`). Consumed in-process by fusion-agent-studio `TrainingService` and exposed over `trainer.*` RPC.
- `bridge/` — **trainer-bridge console (#71)**: FastAPI facade (`server.py`) around the library serving the four-section Trainer GUI (`trainer.html`: datasets / training / merge & publish / evaluation) at `/` on `:8790`. Bridge owns the fusion-mlx admin key + RunManager lifecycle (runs survive console refreshes); loopback bind + bearer token (`FUSION_TRAINER_BRIDGE_KEY`), browser never sees the admin key. Publish promotes a run's **merged standalone model** (auto-enters `/v1/models`); preset registry is a config file (`~/.fusion-trainer-bridge/presets.json`, re-read per request, editable without a release). Tests: `bridge/test_server.py` (mocked RunManager/MLX client). Adapter hot-mount remains deliberately unused — publish promotes a merged standalone model (simpler to serve/version); the old blocker (2-level registry missing slash-id adapters) is fixed upstream (fusion-mlx#1317, PR #1327 — 3-level walk, slash-id adapters listed, verified live through `:11432`). Lifecycle: `scripts/trainer-bridge.sh start|stop|status|log`. The console follows the shell theme (#73): class-based `html.light`/`html.dark` palettes, a pre-paint head script reads `localStorage["fusion.shell.theme"]` (fallback `prefers-color-scheme`), and the embedded iframe listens for the shell theme event `{type:"event", event:"theme", payload:"dark"|"light"}` and flips without reload. **Process title (#77):** `__main__` sets `setproctitle(f"fusion-trainer bridge :{BRIDGE_PORT}")` (core dependency, try/except fallback logs a warning and keeps the default title) — the process shows as `fusion-trainer bridge :8790` in ps/Activity Monitor instead of bare homebrew `Python`; `exec -a` doesn't survive the Python.app argv on macOS, setproctitle is the only reliable mechanism.
- `bridge/shell_registry.py` — **shell module registration (#72)**: registers `bridge/manifest.json` (id `fusion-trainer`, entry `/shell/fusion-trainer/`) with the fusion-gateway shell registry (`POST /api/v1/shell/manifests`) + 15s heartbeat, so the fusion-web-shell sidebar lists 训练控制台 and the gateway proxy is the user-facing entry (bridge stop → greys unreachable; 404/401 heartbeat → re-register). K1 line: no `api_key` in the body → gateway issues an `fm-` key (`raw_key`, once), persisted to `~/.fusion-trainer-bridge/web_module_key` (0600) and used for heartbeat auth; inbound `_auth` dual-accepts the static bridge key + issued key. Env-gated (`FUSION_SHELL_GATEWAY_URL` + `FUSION_ADMIN_KEY`; script defaults URL + reads the admin key from the gateway config). Tests: `bridge/test_shell_registry.py` (mocked HTTP). Upstream note: fusion-gateway#277 (fixed in #278) — Upsert's keep-branch used to drop the issued-key plaintext, leaving the proxy 401 while heartbeats stayed green; requires the fixed gateway.

### Key Design Decisions

1. **Pure HTTP delegation, never direct MLX imports.** Per the project rule, fusion-trainer talks **only** to fusion-mlx's HTTP API. Upstream gaps are filed as issues/PRs against fusion-mlx first, then landing code follows here — do not work around this by importing `mlx-lm`/`mlx-vlm` in-process.

2. **Port default 11434.** `TrainerConfig.mlx_port` defaults to `11434` (fusion-mlx direct). Since fusion-gateway v0.8.4 (fusion-gateway#30, closed) the gateway on `:11432` proxies `/admin/api/fine-tune/*` 1:1 to fusion-mlx — including `/jobs/models` (fusion-mlx#397, closed) — verified live (jobs/adapters/models all 200 through `:11432`; the gateway auth chain validates the client key and injects the upstream credential). The default stays `11434`: one hop less and the trainer's own admin key. Override via `FUSION_MLX_PORT=11432` to route fine-tune through the gateway. The hub (`hub_url`) stays on `:11432` — since fusion-gateway#316 (closed) the gateway proxies the hub's `/api/v1/models` too, so live hub publish works through the gateway with a single gateway key (verified live: voice-package register 201, 409-idempotent, list 200 through `:11432`).

3. **Hub dataset convention.** `hub:sft/code_alpaca` → `{model_hub_path}/datasets/sft/code_alpaca.jsonl`. Hub path (`$FUSION_MODEL_HUB` or `~/fusion-model-hub`) is **read-only** — trainer reads datasets from it, never writes. Outputs go to `cache_path` (`$FUSION_TRAINER_CACHE` or `./runtime_cache`).

4. **Job poll pattern.** Trainers submit a job → `wait_for_job*` polls every 2s until terminal status → `on_progress` callback converts `events` into `ExperimentLogger` metrics. Failures surface visibly (status `failed`/non-`completed` returns error dict, never fakes "completed").

5. **GRPO two backends.** `grpo_backend="rft"` (default): reward-filtered SFT approximation over the existing fine-tune endpoint — sample G, sandbox-score, group-relative advantage, **per-prompt** top-k (each prompt group contributes up to k positives, then merged — never a global sort that lets high-spread groups monopolize), one SFT job. `grpo_backend="grpo"`: real policy-gradient via `/api/fine-tune/grpo/jobs` with a local reward HTTP callback.

6. **Deterministic sandbox reward (Rule 5).** `sandbox.py` computes reward with code, not a model: `code` mode execs in a subprocess with timeout + restricted temp dir (not a full sandbox — untrusted data needs container/seccomp upstream); `math` mode normalizes and compares answers; `off` = uniform baseline. **Security gates (v0.1.11):** CLI `--sandbox` defaults to `off` (not `auto`), so code-mode exec is never auto-triggered by a `tests` field. `reward_code` additionally checks `FUSION_CODE_SANDBOX_TRUSTED=1` before any exec — unset → fail-visible refusal (return 0.0 + error log), never silent. True OS-level isolation is tracked at [fusion-mlx#743](https://github.com/dahai80/fusion-mlx/issues/743). v0.1.13 adds a real macOS seatbelt isolation backend (`sandbox-exec`, `fusion_trainer/rlsl/isolation.py`) auto-selected on Darwin — network denied, tmpfs workspace, read-only interpreter prefix — with rlimit fallback on non-macOS; `FUSION_CODE_SANDBOX_BACKEND` selects. The rlimit prelude still runs inside the seatbelt child as an inner cap. Issue #53. v0.1.14 narrows the seatbelt data-read: the profile now `(import "system.sb")` (pulls in `dyld-support.sb`, solving the dyld-init SIGABRT that previously forced a blanket `(allow file-read* (subpath "/"))`) and confines `file-read-data` to the interpreter prefix + stdlib + lib-dynload + tmpdir, with `file-read-metadata` kept broad (lstat for realpath ancestor walks — leaks directory structure, not contents). Reads of `~/.ssh`, `/etc`, and sibling project source are now denied. Threat model shifts buggy-not-malicious → malicious-capable for data-exfiltration attempts; timing side-channels remain out of scope (#743).

7. **MXFP8 passthrough to 8-bit QLoRA.** `use_mxfp8` defaults to `False`. An explicit `True` now passes `mxfp8=True` through to fusion-mlx ([fusion-mlx#402](https://github.com/dahai80/fusion-mlx/issues/402)/#425 closed), which routes to the 8-bit QLoRA path (`quantize_base=True`, `quant_bits=8`, `fine_tune_type=qlora`) — 8-bit frozen base + LoRA for memory saving, NOT fp8 compute (MLX 0.32 has no fp8 dtype). `mxfp8+full` is a contradiction (full unfreezes the base, nothing to quantize) and still raises `MLXFineTuneError` client-side at job-build time — fail-visible stop before submission. The stale fail-stop that refused all `use_mxfp8=True` was removed once #402/#425 landed.

8. **Reward-server token auth + path validation.** `RewardServer` / `RMRewardServer` generate a one-time token at startup and embed it as `?token=` in the `reward_endpoint` URL handed to fusion-mlx. `do_POST` rejects any path other than `/reward` (404) and any request whose `token` query param fails `secrets.compare_digest` (403). The endpoint URL is passed verbatim with only a `Content-Type` header, so the `?token=` reaches the server intact. A prompt that does not map back to a known dataset sample logs a loud warning (fail-visible reward signal loss).

9. **HTTP connection reuse + retry/backoff (A1).** `MLXFineTuneClient` keeps one pooled `httpx.Client` (closed via `close()`/`__del__`); `_poll_get` retries network errors and 5xx with exponential backoff (max_retries=5) and raises immediately on 4xx. `wait_for_*_job` catches `MLXFineTuneError` from a single failed poll and `continue`s the loop rather than killing a multi-hour run on one transient blip — terminal status is judged by job `status`, not by a single HTTP success.

10. **RunManager singleton + per-instance sinks (A2).** `get_run_manager()` is the double-checked-locking singleton entry (one `RunManager` per process). Sinks live on the instance (`self._active_sinks`), not a module global, so two instances can't cross-talk. CLI uses the singleton. NOTE: the fusion-agent-studio daemon must call `get_run_manager()` (not construct its own) — tracked at [fusion-agent-studio#268](https://github.com/dahai80/fusion-agent-studio/issues/268).

11. **Zombie-job cancel on restart (L3).** `_load_existing_runs` marks a non-terminal run `failed` **and**, if it has a `job_id`, calls the matching `cancel_*_job` against fusion-mlx first. If fusion-mlx is unreachable it still marks failed but warns loudly with the `job_id` so the operator knows the upstream job may still be burning resources.

12. **Logger lifecycle + atomic meta (A3/M2).** `RLSLEngine.run` wraps its `self._logger` in `try/finally: close()` across every early-return path. `_run_thread`'s `FileHandler` attaches to `logging.getLogger("fusion_trainer")` (not root) and is removed in `finally`. `RunManager._persist_meta` writes to `.json.tmp` then `os.replace` (atomic), cleaning up the temp on error — so `run_meta.json` never lands half-written in contradiction with `events.jsonl`.

13. **Publish 409 idempotency + adapter-existence check (L4).** `ModelHubClient.publish_adapter` on a 409 best-effort `list_models(name=name)` (exact, tenant-scoped — [fusion-models-hub#51](https://github.com/dahai80/fusion-models-hub/issues/51) CLOSED) and matches by exact `name` + `base_model_id` — a hit means "already published", returned as `{published: True, idempotent: True}`; a miss (different base) still raises `HubPublishError`. The exact `name=` filter is preferred over the fuzzy `keyword=` (which cannot distinguish "my adapter" from "another model sharing a token"); `keyword=` remains a fallback for older hub versions. `RunManager.publish_run` verifies via `list_adapters` that the adapter weights actually exist on fusion-mlx before posting to the hub, refusing to register a dangling hub entry.

14. **Dataset sample counting + cache (P1).** `RunManager.list_datasets` counts samples via `_count_samples` (parquet → `pyarrow.parquet` row count; text → line count) and caches by `(mtime, size)` so a GUI refresh doesn't re-scan the whole hub.

15. **Contract integration test (M1).** `tests/test_contract_integration.py` (marker `integration`) runs a real minimal SFT job against a live fusion-mlx and asserts the actual returned field names (`adapter_path`, `adapter_name`, job `status`, health `data[].id`, adapter `name`) — catching upstream field renames that mock-based tests miss. Auto-skips when no server is reachable; run explicitly with `pytest -m integration` (CI/nightly).

16. **RunManager audit log + api-key gate (enterprise #2).** `RunManager.__init__` opens an `AuditLog` (append-only JSONL) at `{cache_path}/audit.jsonl`. The 5 mutating ops (`start_sft`/`start_rlsl`/`stop_run`/`publish_run`/`delete_adapter`) each call `self._audit_op(action, run_id, detail, ok, api_key)`, which (a) checks the `ApiKeyGate` — raises `PermissionDeniedError` on mismatch, after recording an `ok=False` audit entry so the rejected op is still in the trail — then (b) records an audit entry. `ApiKeyGate` is enabled when `FUSION_TRAINER_API_KEY` is set (constant-time compare); unset = local-trust (allow all), appropriate for single-user Mac. Actor = `FUSION_TRAINER_ACTOR` (default `local`). `info()` reports `api_key_required` + `audit_log` path. `publish_run` takes `trainer_api_key` (distinct from the hub `api_key`) so a deployment can gate ops without sharing the hub secret. The audit trail is for accountability, not forensic non-repudiation (no signing — local-first file, tamper-protection out of scope).

17. **Prometheus metrics file export (enterprise #3).** `ExperimentLogger.export_prometheus` + module-level `export_prometheus_snapshot` write a `.prom` text-format snapshot: one gauge per scalar metric key (`fusion_trainer_<sanitized>{run="<id>"} <value>`), names sanitized to the Prom `[a-zA-Z_:][a-zA-Z0-9_:]*` grammar. `RunManager._export_run_metrics` emits `{cache_path}/runs/<run_id>/metrics.prom` at run end with `run_steps_total`/`run_total_steps`/`run_status_code` (0 running/1 completed/2 failed/3 cancelled), deterministic from record state (Rule 5), fail-visible. A scrape endpoint is upstream (fusion-agent-studio) — fusion-trainer has no HTTP server, so this is a file export for a node-exporter textfile collector / sidecar.

18. **VLM fine-tune wiring (#55, fusion-mlx #797/#800).** `SFTTrainer._run_training` branches on `self.sft_cfg.model_type == "vlm"` inside its existing E4 try/finally: the VLM path calls `_submit_vlm_job` instead of staging a chat-messages jsonl + `create_job`. The VLM endpoint (`POST /admin/api/fine-tune/vlm/jobs`, admin prefix required) drives `mlx_vlm.trainer` SFT/LoRA inside fusion-mlx — same pure-HTTP-delegation rule, fusion-trainer never imports `mlx-vlm`. `_build_vlm_config` emits ONLY the upstream `VLMFineTuneConfig` field set (no `lr_schedule`/`mask_prompt`/`quant_bits`/`quantize_base`/`mxfp8`/`lora_target_modules` — `VLMFineTuneConfig(**body)` raises `TypeError` on unknown keys → upstream 400). `_submit_vlm_job` does NOT call `stage_dataset`: mlx-vlm's `load_dataset` consumes a HF dataset id or a local dir of images + jsonl directly; the dataset ref is resolved from `dataset.path` or `dataset.hub_dataset` (hub convention, same path-traversal guard as `DatasetLoader._resolve_path`). `wait_for_vlm_job` mirrors `wait_for_job` (A1 retry-on-poll-failure + cancel) on the VLM poll path. VLM QLoRA caveat: `VLMFineTuneConfig` has no quantize field, so `method="qlora"` on a VLM run degrades to plain LoRA with a loud `logger.warning` (fail-visible) — no base quantization occurs. The `sft_vlm_7b_qlora` preset's `quant_bits` is therefore advisory-only on the VLM path. Result dict carries `model_type="vlm"`.

19. **BNUP two-stage training pipeline (#56/#57/#58/#59).** The BNUP pipeline (北师大版 K-12 math) runs SFT → DPO → merge via three new CLI commands: `bnup-prep` (data prep), `bnup-train` (orchestration), `merge` (adapter → SafeTensors). **Data prep (#56):** `bnup_prep.py` validates DSL via fusion-core `validate_dsl_str` (single source of truth — no duplicated schema), builds `<thinking>`+`<dsl>` ShareGPT samples, skips invalid with count logged. `bnup_dpo_prep.py` generates preference pairs from SFT output using the negative factory (#57). **Negative factory (#57):** `bnup_negatives.py` has 5 static generators producing syntactically distinct negatives (broken JSON, direct answer, wrong visual_type, missing tag, format drift) — each designed to FAIL DSL validation (true negatives, not false) — plus a 6th semantic generator `make_param_drift` (sft-dpo-1013 §2.4, E1 top failure class: rewrites one `params.<name>` eval reference to a drifted name — Chinese synonym / abbreviation / case / suffix; JSON+schema stay valid, fails only at eval execution with KeyError; 2 priority slots in `generate_negatives`). `generate_negatives` picks up to `neg_ratio` (max 5) distinct per sample. **Merge (#58):** `merge.py` calls fusion-mlx `POST /v1/merge-adapter` (admin-gated, convert router) — pure HTTP, never imports `mlx_lm`. `MLXFineTuneClient.merge_adapter` is a synchronous call (blocks until merge done, `max_retries=1` — a merge is not a pollable job). Optional `--quantize 4bit|8bit` calls `/v1/quantize` post-merge. `merge_and_export` now generates a post-merge Socratic-format sample (`generate_validation_sample` → `chat_completions` + `DEFAULT_VALIDATION_PROMPT`) and runs `validate_merged_model` to check `<thinking>`+`<dsl>` format — best-effort, fail-visible warning on generation error (never gates the merge). `ft merge --publish` registers the merged model in fusion-model-hub via `ModelHubClient.publish_merged_model` (`model_type="mlx"`, no `base_model_id` — a merged model is standalone, not a LoRA adapter; idempotent on 409). `validate_merged_model` checks `<thinking>`+`<dsl>` format on generation output (JSON parseability, not full schema — use fusion-core for that). **DPO adapter chaining (fusion-mlx #1149, closed via PR #1152):** upstream's DPO endpoint now accepts `init_adapter_path` — the policy model loads with the SFT adapter before DPO training; the reference model stays base-only (DPO theory). `RLSLConfig.init_adapter_path` flows into `_build_dpo_config`/`_build_orpo_config` and is only included when non-empty (empty = fresh LoRA, backward compat). The BNUP `pipeline` stage auto-captures the SFT result's `final_model_path` and passes it to the DPO stage's `init_adapter_path`; the `merge` step then merges the DPO adapter (carrying the SFT→DPO signal) with the base. Standalone `ft rlsl --method dpo --init-adapter-path <p>` and `ft bnup-train --stage dpo --init-adapter-path <p>` chain manually. **Preset module:** `fusion_trainer/presets/bnup.py` is the single source for BNUP presets — `BNUP_SFT_32B`/`BNUP_DPO_32B` (sourced from `sft/presets.py` + `rlsl/presets.py`, no duplication) + `BNUP_PIPELINE` (orchestration config: `sft_preset`, `dpo_preset`, `chain_adapter`, `merge`). **Config mapping:** spec uses LLaMA-Factory field names (`finetuning_type`, `cutoff_len`, `warmup_ratio`); fusion-trainer maps to its own schema (`method=qdora`, `max_seq_length`, `warmup_steps`). **QDoRA (#63):** `method="qdora"` maps to fusion-mlx `fine_tune_type="dora"` + `quantize_base=True` + `quant_bits=8` — frozen 8-bit quantized base + DoRA adapters (mlx_lm 0.31.3 `DoRALinear.from_base` accepts `QuantizedLinear`). Live-verified end-to-end on Llama-3.2-1B-Instruct-4bit: base quantized, DoRA adapters (`lora_a`/`lora_b`/`m`) trained, adapter mounted for inference. `bnup_sft_32b` uses `method=qdora` + `quant_bits=8` per the PRD baseline.

20. **SFT checkpoint resume + engine-restart detection (#65, fusion-mlx #1182).** Requires fusion-mlx v0.10.12+. **Resume path:** `ft sft --resume` / `ft bnup-train --stage sft|pipeline --resume` resolves `~/.fusion-mlx/adapters/<model>/<run-name>/` via `find_latest_checkpoint` (highest `NNNNNNNN_adapters.safetensors`), stages it to `{output_dir}/resume_stage/adapters.safetensors` (upstream `#1182` loads exactly `adapters.safetensors` — staging also protects the source checkpoint from the resumed job's first save), sets `SFTConfig.init_adapter_path` → `_build_mlx_config` emits `init_adapter_path`, and subtracts the checkpoint step from `iters` (upstream step counter restarts at 0 — weight resume, not optimizer-state resume). Fully-trained → completed no-op result pointing at the checkpoint, no job submitted. No checkpoint → loud warning + fresh start. VLM path warns + starts fresh (`VLMFineTuneConfig` has no resume field upstream). **Engine-restart detection:** `MLXFineTuneError.status_code` carries the HTTP status; a 404 job poll raises immediately via `_raise_if_job_lost` (all 5 `wait_for_*_job` loops) instead of zombie-polling to the 24h deadline; a `cancelled` terminal status (fusion-mlx restart recovery marks RUNNING/QUEUED jobs cancelled — user cancel raises instead) gets the same treatment. Both yield an `interrupted` result with `resume_checkpoint`/`resume_step` + a printed `--resume` hint. **Liveness state:** `job_state.json` under the run output dir (`job_id/model/adapter_name/adapter_dir/step/resume_step/status/updated_at`), written atomically (`os.replace`) at submit, on every step change (`_ingest_progress`), and on every terminal path — engine-side `os._exit` bypasses atexit, so state is only as durable as the last poll. **Data-path contracts fixed along the way:** `deduplicate` serializes chat turns (messages/conversations) into the dedup key (the E5 code dropped every chat sample while its docstring said keep); `DatasetLoader.load_sft` sniffs the dominant schema and routes chat datasets through `load_messages` (the flat `load()` `_normalize` drops samples without input/output fields — a chat SFT dataset loaded with 0 samples); `_apply_extras` now passes YAML `save_every`/`log_every`/`quant_bits`/`max_steps` (silently dropped before — `save_every: 50` ran at default 500 and wrote no numbered checkpoint, leaving `--resume` nothing to resume from). Live-verified on Llama-3.2-1B against fusion-mlx 0.10.12: checkpoint write → engine restart mid-run (step 128) → `interrupted` report with checkpoint → `--resume` continues (engine log `Resumed adapter weights ... #1182`, `iters=480-128=352`) → completed. `tests/test_sft_resume.py` (18 tests) covers discovery, staging, iters subtraction, 404 fast-fail vs transient retry, job-state persistence, interrupted result, resume no-op.

21. **TTS voice-pack fine-tune (#74, fusion-mlx #1336).** `ft voice-train` trains a Kokoro voice pack over fusion-mlx `POST /admin/api/fine-tune/voice/jobs`; upstream is gradient-free SPSA over the voice-pack rows (style pack `[510,1,256]` safetensors), so there is no adapter — the artifact is a package at `~/.fusion-mlx/voices/<voice_id>/voice.safetensors` served as `voice_ref` on `POST /v1/audio/speech` (unknown ref → 404, no silent fallback). `VoiceTrainConfig` mirrors the upstream field set exactly (`steps`, `learning_rate`, `perturbation`, `decay`, `base_voice`, `lang_code`, `max_samples`, `dynamics_weight`, `level_weight`, `anchor_weight`, `seed`) because unknown keys 400; `VoiceTrainer` rejects non-Kokoro model ids client-side for the same reason upstream does. **Dataset layouts:** `metadata.csv` (`file|text`), `metadata.jsonl` (`{audio,text}`), or bare `<name>.wav` + `<name>.txt`; `validate_voice_dataset` fails loudly on missing audio, `< 1 KiB` files (truncated) and empty transcripts before submitting. **Progress:** the job GET carries no `events` array — upstream reports progress over SSE (`/jobs/{id}/stream`); `wait_for_voice_job` therefore polls status only, with A1 retry-on-poll-failure and 404 fast-fail via `_raise_if_job_lost`. **Hub registration (M-C):** `publish_voice_package` posts `model_type=audio` (hub `ModelType.AUDIO`; there is no `voice` enum value) with the `voice_ref` in the description; weights stay on fusion-mlx, the hub entry is the ownership/versioning record; 409 is idempotent on exact name. Live `--publish` verified end-to-end (2026-10-26, fusion-gateway#316 closed): gateway `:11432` proxies the hub's `/api/v1/models`, so `hub_url=http://localhost:11432` + a gateway key registers the voice package (201 → model_id, 409-idempotent on re-publish, entry visible via gateway keyword search, model_status=draft pending hub-side approval). Hub-direct (`:11444` + `FUSION_MODEL_HUB_API_KEY`, client sends `X-API-Key`) remains as fallback. Tests: `tests/test_voice_trainer.py` (24 tests, mocked HTTP) + hub header assertions in `tests/test_hub_client.py`. Training loop live-verified earlier: CLI → job → completed → package on disk → `voice_ref` synthesis 200 with a real WAV; spectral distance improved (0.136 → 0.076, `beat_stock_voice: true` on all 3 real jobs).
22. **Benchmark-based checkpoint selection + nightly real-training CI (#75).** `ft sft --eval-select` runs the post-training eval loop (`eval_loop.py`): every numbered checkpoint gets one fusion-bench task (`params.adapter_path` = staged servable dir — the #65 resume_stage trick), the winner is picked deterministically (bench score higher-wins/tie→later-step; val_loss lower-wins fallback; last checkpoint last resort), and the table persists atomically to `{adapter_dir}/checkpoint_selection.json`. **Fail-visible, never fatal:** bench unreachable → all rows `unavailable` + persisted `fallback_reason` + val_loss selection; no checkpoints at all → single-row `single_checkpoint` table. **Upstream passthrough landed:** fusion-bench v0.4.11 ([fusion-bench#29](https://github.com/dahai80/fusion-bench/issues/29), closed) forwards `params.adapter_path` to fusion-mlx chat as `adapters`, so bench scores reflect the true checkpoint weights. The params form (not the new top-level `adapter_path` field) is sent deliberately — older bench releases 400 on unknown top-level keys while every release reads `params.adapter_path`. Bench auth is fusion-identity tenant auth (`X-Tenant-Id` + Bearer JWT, fail-closed upstream) — live scoring needs operator-issued credentials; the contract is pinned by mocked tests (`tests/test_eval_loop.py`, 33 cases). **GRPO honesty:** `grpo_backend` accepts `policy_gradient` as an alias of `grpo` (normalized in `TrainerConfig.__post_init__`); docs state the default `rft` is a reward-filtered SFT approximation (RFT/RAFT-style), not true GRPO. **Loader truncation fix:** `load_messages` now budgets the WHOLE conversation at `max_seq_length * 4` chars (≈4 chars/token; exact token-level truncation stays upstream at batch assembly), trimming whole trailing turns so the chat template stays well-formed — the old per-message `[:max_seq_length]` char cap was a ~4x over-truncation treating tokens as chars. **Packing is wired (rc16)** — [fusion-mlx#1400](https://github.com/dahai80/fusion-mlx/issues/1400) closed: `FineTuneConfig.pack_sequences` (fusion-mlx >= 0.10.17, upstream `training/packing.py` supplies the packed iterator + block-diagonal masked loss). `ft sft --pack-sequences` / YAML `pack_sequences: true` / `ft bnup-train` `_pick` all flow into `_build_mlx_config`, which sends the key ONLY when on (older fusion-mlx 400s on the unknown key). Off by default: changes batch composition. Live-verified on Llama-3.2-1B (job record `pack_sequences: true`, completed). **Nightly CI** (`.github/workflows/nightly.yml`, macOS arm64, cron 18:30 UTC + `workflow_dispatch`): provisions `~/.fusion-mlx/settings.json` with a known `auth.api_key` (admin router is fail-closed — a fresh install 401s every fine-tune call), boots `fusion-mlx serve --model Qwen3-0.6B-4bit` `--profile standard` (lite auto-detect on <24GB runners unmounts the convert router), waits on `/v1/models` (Bearer), then runs `TestRealFusionMLXIntegration` + contract tests with `FUSION_TRAINER_REAL=1` — the ~18 real-loop tests the ubuntu push-CI silently skips (no MLX Linux wheel). Installs base (slim) `fusion-mlx>=0.10.17` — valid since [fusion-mlx#1403](https://github.com/dahai80/fusion-mlx/issues/1403)/#1406 made the turboquant attention patch pass through without `mlx_vlm`; running slim keeps the slim path regression-covered.

23. **Eval flywheel: trajectory ingestion + round curve (#76, items 11+12).** Consumes fusion-eval#6 trajectory exports to close the eval→train→re-eval loop. **Ingestion:** `ft datasets from-eval --export <trajectories.jsonl> --output <sft.jsonl> [--dpo-output <dpo.jsonl>]` (`dataset/eval_ingest.py`) — passed-only trajectories become `{"messages": [...]}` SFT samples (multi-turn preserved); `--all` exports additionally mine tasks with BOTH a passed and a failed trajectory into `{"prompt","chosen","rejected"}` DPO pairs (unpaired failures counted loudly, never fabricated). Every from-eval dataset gets an atomic sidecar manifest `<output>.from_eval.json` carrying the export sha256. **Traceability:** `ft sft` detects the sidecar automatically (`_find_eval_manifest`) and records `source_export_sha256`/`source_export_path` in the run result. **Round registry:** `ft flywheel record --label <name> --summary <summary.json> --checkpoint <dir-or-model> [--export ...] [--dataset ...]` (`flywheel.py`) appends `{round, label, pass_rate, per_type, export_sha256, eval_run_id, checkpoint}` to `{cache_path}/flywheel.json` (atomic write); `ft flywheel status` prints the pass-rate-vs-round curve with deltas + per-type table. **Round chaining:** `--init-adapter-path` on `ft sft` (mirrors `ft rlsl`) reuses the #65 `_resolve_resume` staging path — final-weights dirs train full iters from loaded weights (step 0), numbered checkpoints subtract their step. **Memory safety:** `SFTConfig.gradient_checkpointing` (`--grad-checkpoint`) passes through to fusion-mlx `FineTuneConfig.gradient_checkpointing` (LM) / `grad_checkpoint` (VLM), key sent only when on — 27B-8bit + seq 4096 without it exhausted unified memory and panicked macOS 3× on 2026-10-26; with `--grad-checkpoint --max-seq-length 1024` the same run completes (~8 min). **Loader hardening (lone-assistant fix):** when the #75 trim loop kept trailing assistant turn(s) but dropped every user turn, the sample went upstream as a lone-assistant conversation and the job died with `TemplateError: No user query found in messages` — the fallback now always re-prepends the last user query (hard-sliced), keeping samples template-valid. Flywheel rounds are run strictly serial (train → unload → eval → record) per the machine-safety constraint. **Real-round evidence (rc19, Qwen3.8-27B-8bit, 30-task eval set):** baseline 53.33% → fw-round1 73.33% (+20pp) → fw-round2 63.33% (−10pp), trend first→last +10pp UP — the curve registry recorded all three with export sha256s (`ft flywheel status`). Zero-type acceptance exceeded: `long-context` and `multi-turn-repair` flipped 0→1 and held at round-2. Round-2 regression isolated honestly: `testwrite` 3/3→0/3, all three hits of the 900s timeout — chaining two SFT rounds on the 22-sample eval-fed dataset over-fit (the chained adapter over-produces on test-writing tasks); DPO mining stayed honest-zero (single-arm eval → no passed/failed siblings → 0 pairs, 8 unpaired failures counted loudly). Stopped at round 2: acceptance met, a third round on the same data would deepen the over-fit. **#78 residuals (rc20):** (1) DPO single-arm gate — `--dpo-output` on a single-arm export (every task exactly one trajectory; the shape of every `fusion-eval run --arm <one>` export) now raises `EvalIngestError` with the multi-arm remediation instead of silently writing a 0-pair file; `--dpo-anyway` escapes (warns + writes empty); manifest carries `arms` + `dpo_structurally_empty`; gate live-verified on the real round-2 export. (2) Feature-type 0/3 root-caused across rounds: round-1 failures were spec-gap (t3 wrote only the test file, never implemented slugify; t5 correct `to_roman` but missed hidden out-of-range checks `to_roman(0)` must raise), round-2 failures were all 900s timeouts with CORRECT diffs — the same chained-overfit over-production signature as testwrite, not a capability gap. (3) Round-3 experiment: fresh round-2-eval data (19 samples, never trained on) chained from fw-round2 — directly tests whether the timeout mode is overfit-driven. **Round-3 result (2026-10-28, eval run `20261028-r3-eval`, export sha `504298d3986c`): 14/30 = 46.67%.** Curve now baseline 53.33% → fw-round1 73.33% → fw-round2 63.33% → fw-round3 46.67% (first→last −6.67pp DOWN; honest negative result, recorded via `ft flywheel record`). Hypothesis refuted in part: testwrite RECOVERED 0/3→2/3 (the round-2 collapse was overfit-driven, not capability loss), but feature stays 0/3 across ALL rounds (persistent spec-gap, not overfit) and fresh-data chaining still degraded overall — refactor-multi 1.0→0.0 (t14 IndentationError, t15 missing `user.py`, t16 infinite recursion), configfix 1.0→0.0 (t17/t18 900s timeouts, t19 missed key-rename), long-context 1/1→0/1, depfix 1.0→0.6667; dag improved 0.6→0.8. Conclusion: degradation is cumulative over-production from chained SFT rounds, not purely overfit to trained data — the flywheel's value (round-1 +20pp) came from the first high-signal round on failure data, not from repeated chaining. Adapter not kept mounted (base 27B-8bit TTL-unloaded post-eval).

## GUI Integration (fusion-studio)

Fusion-Trainer is also drivable from the **fusion-studio** desktop client (SwiftUI) — not just the CLI. The GUI never imports `mlx-lm`/`mlx-vlm`; it reaches fusion-trainer **in-process through fusion-agent-studio** over the studio UDS (`/tmp/fusion-studio.sock`, JSON-RPC 2.0).

```
fusion-studio TrainerView → TrainerBridge → IPCClient.trainer* (UDS)
  → fusion-agent-studio TrainerDispatcher (trainer.* RPC, PR #167)
    → fusion-trainer RunManager (fusion_trainer/run_manager.py)
      → MLXFineTuneClient → fusion-mlx HTTP
```

- **GUI panel:** `fusion-studio/FusionStudio/Modules/Trainer/TrainerView.swift` — 6 tabs (训练运行 / 启动训练 / 预设 / 数据集 / 适配器 / 环境信息). State layer: `System/TrainerBridge.swift` (`@MainActor` ObservableObject). IPC wrappers: `Bridge/IPCTrainerMethods.swift`.
- **Trainer-side surface:** `RunManager` (fusion_trainer/run_manager.py) provides async run start + live progress events + registry + presets/datasets/adapters listing + stop. Consumed in-process by `agent_runtime/training_service.py` (TrainingService) and exposed over RPC by `agent_runtime/dispatchers/trainer.py` (18 handlers, namespace `trainer.*`).
- **Upstream PRs:** fusion-agent-studio #167 (RPC widening) + fusion-studio #176 (GUI panel). See `architecture/fusion-trainer-gui.md` for the high-fidelity mockup spec.
- **Limitation:** the GUI path depends on fusion-agent-studio importing fusion-trainer in-process. Real training-loop verification (with fusion-mlx model loading) is done via the CLI path; the GUI is wired but live-end-to-end training is not exercised in fusion-trainer's own test suite.
